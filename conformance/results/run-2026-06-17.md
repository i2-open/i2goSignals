## Submission artifacts

The conformance suite produces a signed per-plan zip via the
`--export-dir` flag of `scripts/run-test-plan.py`. Each zip contains:

- `test-log-<module>-<id>.json` — full per-module log including request
  bodies, response bodies, headers, signature checks, every assertion.
- `test-log-<module>-<id>.sig` — detached signature over the log (suite key).
- `testInfo` payload at the top of each `.json` with `_id` (plan id),
  `testName`, `variant`, `started`, `config`, `exportedAt`, `exportedFrom`,
  `exportedVersion`.

These are the artifacts the OpenID Foundation accepts as evidence in a
certification submission. They sit alongside this report under
`conformance/results/`. The relevant zips for this run are listed in the
Summary table above.

## Findings (final run)

### W1 — `OIDSSFCheckSupportedEventsForStream` warning (all 4 plans)

Module `openid-ssf-stream-control-happy-path` flags 1 warning per plan.
Reproduces identically across push, poll, and CAEP-profile runs. 0
failures otherwise.

**Root cause:** the SUT advertises 14 SCIM event-type URIs in
`events_supported` (`urn:ietf:params:scim:event:feed:*`,
`urn:ietf:params:scim:event:prov:*`, `urn:ietf:params:scim:event:misc:*` —
see `pkg/ssfModels/model_event_types.go`). The suite's check warns on every
URI it doesn't recognise, and it recognises only the CAEP/RISC families. The
SCIM events are emitted by goSignals' SCIM bridge and are a deliberate
feature, not noise.

**Action:** allow-list the SCIM URI family in the suite's expected-warnings
config for this SUT, or trim `events_supported` in a conformance-only build.
Out of scope for this run.

## Changes landed this session (release-0.12.0 working tree)

The CAEP-interop module is interactive — it expects an operator to fire
CAEP events on the SUT during a 60 s delivery window. Closing the gap took
two coupled changes:

### SUT — `internal/server/api_out_of_band.go`

1. **`POST /trigger-event` now accepts the `I2SIG_BOOTSTRAP_TOKEN`
   bearer.** The handler previously required an `admin`/`root` client token;
   `bootstrap-token.sh` cannot mint those because `/register` silently caps
   `admin` out of the requested scopes. Accepting the bootstrap bearer
   (`ScopeKey`) keeps the harness free of out-of-band admin provisioning.
2. **`POST /trigger-event` payload now carries `event_data`.** The handler
   was passing `nil` to `set.AddEventPayload`, producing
   `events: {<caep-url>: null}`. RFC8417 §2.2 requires each event-type key
   to map to a JSON *object*, and the suite's `OIDSSFExtractCaepEventData`
   condition NPEs on `null`. The trigger script supplies the CAEP-1.0 §3
   required fields (`current_status`/`previous_status` for
   device-compliance-change, `credential_type`/`change_type` for
   credential-change, `{}` for session-revoked).
3. **`POST /trigger-event` now submits via `SubmitOperationalEvent` instead
   of `HandleEvent`.** `HandleEvent`'s `MatchesStream` fanout was delivering
   each triggered SET to **every** registered push stream whose iss/aud/
   event-type happened to overlap — including stale streams left behind by
   earlier conformance modules that hold no `Authorization` header. The
   receiver saw those as unauthenticated duplicate pushes
   (`OIDSSFEnsureAuthorizationHeaderIsPresentInPushRequest` failed once per
   leaked stream per event). `SubmitOperationalEvent` is the existing
   point-to-point path used by verify/keepalive code; it delivers to exactly
   the requested sid and bypasses the match loop.

### Harness — `conformance/trigger-caep.sh` (new) and `run-plan.sh` (wired)

`trigger-caep.sh` runs in the background while a CAEP plan executes:

- Authenticates with the bootstrap bearer (no `/register` round-trip).
- Re-discovers the newest CAEP-subscribed stream every iteration so an
  earlier module's stream is never targeted after it's been deleted.
- Gates firing on **two side-channel signals** drawn from MongoDB so we
  never fire into a stream that is currently driving a different module:
  - `STREAM_MIN_AGE_SECS` (default 20 s) — must exceed the
    verification-push/poll modules' stream lifetimes, which are
    short-lived in clean operation.
  - `pendingEvents` count for the stream must be `0` — distinguishes
    "verification test actively polling/pushing SETs" (queue non-empty)
    from "caep-interop in delivery wait" (queue empty).
- Posts the CAEP-1.0 §3 required `event_data` payload per event type.

`run-plan.sh` launches the helper automatically whenever the plan spec
contains `caep`, and traps `EXIT/INT/TERM` to clean it up.


## Historical record — F1 (cleared) and F2 (cleared)

### F1 — auth-header miss on push delivery (CLEARED)

Original 11:33 caep run: `plan=E5mkUhjyFDXh7`, FAILED with two
`OIDSSFEnsureAuthorizationHeaderIsPresentInPushRequest` failures. Initial
suspect: SUT dropping the `authorization_header`. The real cause was zombie
streams from earlier plan runs — goSignals' T3 idle keepalive (default
5 min) fired verification SETs from those streams without an
`Authorization` header (the zombie stream had none configured), and the
suite attributed them to whichever test was active. `run-plan.sh` brackets
every plan with `down -v` + `up -d` + `bootstrap-token.sh`, so no zombie
survives into a later plan.

### F2 — CAEP-interop required operator trigger (CLEARED)

The CAEP plan's `stream-caep-interop` module expects an operator to fire
CAEP events during a 60 s window. The SUT's `POST /trigger-event` endpoint
existed but (a) was unreachable to the bootstrap bearer, (b) emitted
events with null payload, and (c) fanned out to every overlapping stream
including leaked ones. The three SUT changes plus `trigger-caep.sh`
listed above close all three.
