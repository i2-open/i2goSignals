# goSignals v0.12.0-alpha.17

Released: TBD
Compare: [v0.12.0-alpha.16...v0.12.0-alpha.17](https://github.com/i2-open/i2goSignals/compare/v0.12.0-alpha.16...v0.12.0-alpha.17)

## Why this release

**Four defects, each of which made goSignals silently do nothing rather than
fail.** All four were found and fixed on `release-0.12.0` since
`v0.12.0-alpha.16` (2026-07-31), and they share a shape worth naming: a SET was
accepted, verified, persisted and counted — and then not routed, not verified,
or not stored in a form anything else could read. Nothing errored, so nothing
alerted.

- **#259** — every persisted SET was stored Go-shaped, not wire-shaped.
- **#261** — SSTP inbound ignored its own `FORWARD`/`PUBLISH` mode, so two-hop
  SSTP topologies dropped every SET at the middle node.
- **#261 (catalog)** — an event type outside the compiled-in catalog negotiated
  to an empty `events_delivered` and was therefore never routed anywhere.
- **#264** — a transient issuer-JWKS fetch failure was cached forever; the
  `"will retry"` log line never retried, and the stream verified nothing until
  the process restarted.

This alpha also moves the toolchain to Go 1.26.5 and refreshes dependencies
against recent CVE advisories.

## Changes in this repo

### SETs persist in their wire shape (#259, [ADR 0030](../adr/0030-wire-shaped-set-bson-persistence.md))

`goSet.SecurityEventToken` and `goSet.SubjectIdentifier` were persisted by the
mongo-driver's default struct codec, which keys documents by **Go field name**
and ignores the `json:",omitempty"` tags these types carry. RFC 8417 registered
claims were buried in a `registeredclaims` subdocument under Go names (`issuer`,
`audience`, `expiresat`, `issuedat`, `id`) instead of appearing at the top level
as `iss`, `aud`, `exp`, `iat`, `jti`; an opaque subject that is two members on
the wire was stored with all ten identifier variants present and empty. The same
defect reached `subject_filters`, whose `Subject` is a `*goSet.SubjectIdentifier`
too.

`pkg/goSet/set_bson.go` adds `MarshalBSON`/`UnmarshalBSON` on
`SecurityEventToken`, `SubjectIdentifier` and `EventSubject`, routing storage
through a JSON round-trip so the on-disk shape is the wire shape. Alongside it:

- **Read compatibility is a legacy sniff**, not a migration (ADR 0030 D3/D4).
  `UnmarshalBSON` checks the document's top-level keys for markers only the old
  codec could have written (`registeredclaims`, the ten embedded-identifier
  names) and decodes those through the default struct codec. **There is no
  backfill and no dual-write** — old rows are read in place and rewritten in the
  new shape only if something updates them. Upgrading needs no migration step.
- **Persisted integers are pinned to `int64`.** Existing rows keep their
  `int32`; MongoDB compares and sorts numeric types against each other, and
  nothing queries inside `event`, so this is unobservable outside storage.
- **BSON-reserved member names are rejected, and bad rows fail loudly.** A SET
  whose event payload uses a `$`-prefixed member is now unstorable rather than
  stored wrong — an intended trade that converts a silent corruption into a
  visible error.
- Null members are dropped on encode, and `EventSubject` no longer loses its
  `sub`.

### SSTP inbound honours its direction's RouteMode (#261, [ADR 0031](../adr/0031-sstp-inbound-route-mode.md))

An SSTP pair carries a `mode` per direction, `SstpModeToRouteMode` maps the
inbound one onto `SstpInbound.RouteMode`, and `docs/SSTP.md` documented that a
pair can `FORWARD` outbound while `PUBLISH`-ing inbound. **The router never read
it.** `HandleEvent` flagged `sstpInbound = true` and returned unconditionally,
before the `RouteModeImport` check — so every SSTP-ingested SET was treated as
`IMPORT` and consumed locally.

The consequence was that `A --sstp--> goSignals --sstp--> B` never reached B.
Hop 2 now happens whenever the A-pair's inbound direction is `FORWARD` or
`PUBLISH`. A **nil** inbound half is treated as `IMPORT`, matching how persisted
records that predate per-direction mode are read. `docs/SSTP.md` gains an
*"Inbound mode governs routing, not just signing"* section: `FORWARD` and
`PUBLISH` are identical on the inbound leg — both mean "route onward" — and the
verbatim-vs-re-sign choice belongs to each **outbound** stream at delivery time.

### The supported-event catalog is extensible by configuration (#261, [ADR 0032](../adr/0032-extensible-supported-event-catalog.md))

`model.GetSupportedEvents()` was a compiled-in list (SCIM/RFC 9967, CAEP, RISC,
WISE). Because registration negotiates
`events_delivered = events_requested ∩ events_supported` and the router matches
against `events_delivered`, a URI outside that list intersected to nothing: the
stream registered `201`, SETs carrying the type were accepted, verified,
persisted and counted, and matched no stream. `"*"` short-circuited to the same
catalog, so no registration input could reach a private vocabulary.

**New environment variable `I2SIG_EVENT_TYPES_EXTRA`** extends the catalog with
event-type URIs this build has no compiled-in knowledge of. Entries are
comma- and/or whitespace-separated and must each be an absolute URI; a relative
or unparseable entry is skipped with a `WARN` naming it, empty entries are
discarded silently, and duplicates of a built-in (or of each other) are ignored
case-insensitively. Extended URIs then behave exactly like built-ins — advertised
in `events_supported`, resolvable from `events_requested` literally / by pattern
/ via `"*"`, and fanned out over push, poll and SSTP alike.

Three things are worth reading before enabling it (all detailed in
[`docs/configuration_properties.md`](../configuration_properties.md)):

- **Validation.** An extended URI has no built-in payload validator, so it takes
  the *Unsupported* path of whatever `I2SIG_STREAM_EVENT_VALIDATION` mode
  applies. `NONE`/`WARN` forward it, `ENFORCE` forwards it unvalidated, and
  **`STRICT` rejects it** — a deployment carrying a custom vocabulary under
  `STRICT` will reject its own events.
- **Scope in time.** An **SSF stream** negotiates the extended catalog at create
  and again on a `PATCH` carrying `events_requested`. An **SSTP pair** negotiates
  only at create — `PATCH` on a pair is a narrow whitelist that does not touch
  events, so a pair provisioned before the vocabulary was configured must be
  recreated.
- Removing a vocabulary from the variable does **not** retract it from records
  that already negotiated it.

`events_supported` is now also correctly honoured as Read-Only on registration.

### Unresolved issuer JWKS is retried, not cached (#264, [ADR 0033](../adr/0033-jwks-url-presence-discriminates-expected-verification-material.md))

`StreamService.GetIssuerJwksForReceiver` treated **entry presence** in the
per-process `receiverStreams` map as a cache hit and returned `ValidateJwks`
verbatim — including when it was `nil`. `fetchReceiverJwks` collapsed three
unrelated outcomes into that same nil: a configured URL whose fetch failed
transiently, no URL configured at all, and a disabled SSTP inbound direction. So
the transient case logged `"Temporary error loading JWKS, will retry"` and then
never retried; the stream verified nothing until the process restarted.

ADR 0033 makes **issuer-JWKS-URL presence** the discriminator between "nothing
is expected here" and "something is expected and missing". The fix:

- **New `pkg/services/receiver_jwks_cache.go`** — a real cache with retry, keyed
  by record identity. Entries are evicted **by record identity** on delete, so a
  recreated stream cannot inherit a stale entry.
- Issuer JWKS is resolved **from a snapshot**, not the shared record, closing a
  read/write race on the cached entry.
- Status changes are mirrored into the receiver cache, and a re-enabled stream
  **unlatches** rather than staying stuck.
- A pair that violates the **ADR-0066** §D2 (family) invariant now disables
  **both directions**, and a permanent-JWKS disable routes through the
  per-direction rule; the status routing rule accepts either pair signal.

**New operator-facing readiness surface.** Stream *status* deliberately keeps
reporting `enabled` for a stream whose issuer JWKS cannot be resolved, so
readiness is reported separately and is **node-local and derived — never
persisted, and not part of the SSF wire-format `StreamConfiguration`**:

- `pkg/ssfModels.JwksReadiness` with states `ready`, `unresolved` (carries the
  last error and, when scheduled, the next attempt time) and `not-configured`.
- `jwks_readiness` / `inbound_jwks_readiness` on the admin stream-state
  surfaces, overlaid via the new `StreamService.OverlayJwksReadiness` because
  DAO-sourced records never carry it.
- Prometheus gauge **`goSignals_router_stream_jwks_readiness_info`**, labelled
  `stream_id` / `direction` / `readiness`. Transmit-only streams emit no series.

Two cluster members may legitimately disagree on readiness during a partial
outage, and neither is stale — it describes *this* node's reachability, not a
property of the stream.

## Compatibility

**The exported library surface is additive — nothing was removed.** New in
`pkg/`: the three `MarshalBSON`/`UnmarshalBSON` pairs in `goSet`,
`ssfModels.JwksReadiness` (+ its states and `DeepCopy`),
`ssfModels.EnvEventTypesExtra`, and `StreamService.OverlayJwksReadiness`.
Consumers re-pinning to this tag recompile without source changes.

Behavioural changes an operator should know about:

- **SSTP inbound in `FORWARD`/`PUBLISH` now routes onward.** If a deployment was
  relying — knowingly or not — on the old unconditional `IMPORT` behaviour to
  stop SETs at the middle node, set that direction's mode to `IMPORT`
  explicitly.
- **Newly written events and subject filters use the wire shape.** Anything
  reading the `events` or `subject_filters` collections directly (rather than
  through `pkg/goSet`) sees top-level `iss`/`aud`/`exp`/`iat`/`jti` on new rows
  and the old `registeredclaims` layout on untouched ones. There is no backfill.
- A SET whose event payload carries a `$`-prefixed member is now **rejected**
  rather than silently stored wrong.
